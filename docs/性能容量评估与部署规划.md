# 性能容量评估与部署规划（5000 人规模）

> 版本 v1.0｜2026-09-12｜状态：**规划文档（demo 阶段暂不实施）**
> 评估依据：当前代码架构实况（server/ 零依赖栈、receiver/ 收流、db.js 数据层）+ 5000 人负载模型推算。
> 结论有效性：以 D13~D17 时期的代码结构为基线；若数据层/部署方式发生重构，需重新评估。

---

## 0. 结论速览

| 问题 | 答案 |
|---|---|
| 当前架构能撑多大？ | **500~800 活跃用户内安全；2000 人开始吃力；5000 人必须做架构加固** |
| 是否需要推倒重来？ | **不需要**。数据访问集中在 db.js 一层、前端纯静态、API 无状态倾向，演进是"分层加固"不是"重写" |
| 真正的瓶颈 | ①同步 SQLite ②单进程 ③LLM 分析无队列（详见 §2） |
| 最大运营成本 | **ASR 转写**（讯飞按并发/时长计费，估算数万元/月），LLM 反而便宜（<2 千/月） |
| Demo 阶段动作 | **不改代码**，但触发条件（§5）一旦命中立即启动阶段一加固 |

## 1. 负载模型（5000 人意味着什么）

> 原则：用户规模 ≠ 并发。按"全员模式待机 + 录音角色业务使用"的双模式产品形态推算。

| 指标 | 估算值 | 推算依据 |
|---|---|---|
| 员工总数 | 5000 | 需求输入 |
| 日活 | 3000~4000 | 内部使用按 60~80% |
| 录音授权角色 | ~500-800 人 | 销售顾问类岗位占比（05 册双模式：全员待机 / 录音角色激活） |
| **峰值并发录音路数** | **100~200 路** | 录音角色的 10~20% 处于沟通中 |
| 单路推流带宽 | ~30kbps | Opus 20-25kbps + WS 帧开销 |
| 峰值入流带宽 | ~6Mbps | 200 路 × 30kbps，对服务器压力很小 |
| 日增录音时长 | ~2500 小时/天 | 500 人 × 4 场 × 45 分钟 |
| **日增音频存储** | **~22GB/天** | 20kbps ≈ 9MB/小时 |
| 音频存储峰值 | **~4TB** | 22GB × 180 天留存（07 册 CMP-08），之后进入删除/归档稳态 |
| 日增沟通场次 | ~2000 场/天 | LLM 分析触发量 |
| ASR 转写量 | **75,000 小时/月** | 讯飞实时听写按并发包/时长计费——**成本大头，需商务询价**（粗估数万元/月） |
| LLM 分析量 | ~1800 万 tokens/天 | DeepSeek 价格下约 30~50 元/天，**成本可忽略** |

## 2. 当前代码的七个风险点（按严重度，逐条对应代码）

| # | 风险 | 代码位置/依据 | 5000 人规模下的表现 | 严重度 |
|---|---|---|---|---|
| R1 | **同步 SQLite**：node:sqlite 的 DatabaseSync 每次查询阻塞事件循环 | db.js 全部查询 | 并发请求串行化，页面从毫秒级劣化到秒级 | 🔴 高 |
| R2 | **单进程**：API（8200）与收流（8100）各一个 Node 进程，单核 | index.js / receiver.js | 单核打满全员卡顿；进程故障全员不可用 | 🔴 高 |
| R3 | **LLM 分析无队列**：沟通入库即触发 DeepSeek 调用，无并发限制/重试 | index.js analyze 触发点 | 峰值每分钟数十场并发调用 → 供应商限流、内存堆积 | 🔴 高 |
| R4 | **关键表无索引**：仅 config_items 有 domain 索引；communications(owner/status/created_at)、audit(ts) 均无 | db.js SCHEMA | 列表查询与审计写入随数据量线性劣化 | 🟡 中 |
| R5 | **看板全表内存聚合**：dashboardStats 拉整段时间全部沟通行进内存计算 | index.js dashboardStats | 数据达数十万行后看板打开数秒 | 🟡 中 |
| R6 | **音频存本地磁盘**：单机盘，无自动归档执行保障 | receiver 落盘 sessions/ | 磁盘写满即全站故障 | 🟡 中 |
| R7 | **会话存内存 Map**：重启全员掉线；服务单点 | index.js sessions Map | 每次发版全员重新登录；无高可用 | 🟢 低（内部可接受） |

**不受瓶颈影响的部分**（当前设计天然可扩展）：前端纯静态多页（无构建、可任意加 CDN/Nginx 缓存）、API 无状态倾向（除 sessions 外无本地态）、WS 协议自研可控。

## 3. 两阶段演进方案

### 阶段一：低成本加固（适用 ≤1000 人，工作量约 1 周）

| # | 动作 | 说明 | 触改范围 |
|---|---|---|---|
| A1 | SQLite → PostgreSQL | 数据访问全在 db.js 一层，改动集中；node:sqlite 换 pg 包 | db.js |
| A2 | 补索引 | communications(owner,status,created_at) / audit(ts) / customers(owner) | db.js SCHEMA |
| A3 | LLM 分析进队列 | 并发限 5 + 失败重试 3 次 + 死信记录 | index.js / analysis.js |
| A4 | Nginx 反代 + 静态缓存头 + HTTPS | 静态页强缓存（带版本号），API 透传 | deploy/ |
| A5 | 音频独立目录 + 归档脚本 | 按 CMP-08 留存策略自动清理/下沉 | receiver / 新增 cron |
| A6 | 每日自动备份 DB | 修复 D10 教训在生产侧的延伸 | deploy/ |

### 阶段二：标准生产架构（适用 1000 → 5000 人，随产品化推进）

| 层 | 方案 |
|---|---|
| 应用 | API 2~4 实例（Docker，deploy/ 已有雏形）；sessions Map → Redis/JWT（解决 R7） |
| 收流 | receiver 独立部署按设备号分片路由（WS 有状态）；转写解码Worker 独立扩容 |
| 数据库 | PostgreSQL + 读写分离（看板走从库，解 R5）；communications 按月归档表 |
| 队列 | Redis + BullMQ 承载「转写→分析→预警」管道（解 R3） |
| ASR | 讯飞企业版并发包（峰值 200 路）+ 双供应商热备（06 册 AI-01 既定策略） |
| 存储 | MinIO/OSS 对象存储；音频 180 天生命周期自动下沉/删除（解 R6） |
| 网关 | Nginx/LB：HTTPS、静态缓存、WS 按 deviceFp 一致性哈希分流 |
| 监控 | 三告警先行：WS 连接数、分析队列深度、DB 慢查询；PM2/Docker + Grafana |

### 硬件参考（5000 人 / 峰值 200 路并发）

| 角色 | 规格 | 数量 |
|---|---|---|
| 应用服务（API+receiver 分开） | 8C16G SSD | ×2 |
| 数据库（PostgreSQL） | 4C16G SSD | ×1（+备机×1 可选） |
| 音频存储 | 5~10TB（或对象存储服务） | — |
| 带宽 | 入流 ~6Mbps；公网音频回听按需另计 | — |

## 4. 成本结构提示（规模化后的月度大头）

| 项 | 量级 | 备注 |
|---|---|---|
| ASR 转写 | **数万元/月（最大项）** | 按并发包询价；双供应商比价（06 册 POC） |
| LLM 分析 | ~1-2 千元/月 | DeepSeek 价格下可忽略 |
| 服务器 | 数千元/月 | 阶段二规格 |
| 存储 | 数百~千元/月 | 对象存储 + 生命周期管理 |

## 5. 触发条件（什么时候必须启动加固）

**阶段一（A1~A6）任一命中即启动：**
- [ ] 日活员工 > 500
- [ ] 峰值并发录音 > 50 路
- [ ] communications 表 > 10 万行，或列表/看板打开 > 2 秒
- [ ] 出现第一次因进程重启导致的集体掉线投诉

**阶段二任一命中即启动：**
- [ ] 签约客户/员工总数突破 2000
- [ ] 多企业/多租户需求立项（数据隔离要求升级）
- [ ] ASR/LLM 供应商限流告警出现
