# BadgeCore 固件自研评估与功能规划

> 版本 v0.1｜2026-09-12｜状态：待拍板
> 背景：当前开发载体（微雪 ESP32-S3-Touch-AMOLED-1.75C）运行小智官方固件 v2.4.2，评估自研固件以支持品牌化/推屏/锁定配置/设备绑定/触摸 UI 等定制能力。

---

## 1. 可行性结论：完全可行，路线是「Fork 小智」而非从零写

| 依据 | 说明 |
|---|---|
| **开源协议允许** | 小智固件（[78/xiaozhi-esp32](https://github.com/78/xiaozhi-esp32)）为 **MIT 协议**：免费使用、修改、商用均可，仅需保留版权声明 |
| **这块板子已被适配** | 小智官方提供 1.75C 专用构建——屏幕（CO5300 QSPI 466×466 圆屏）、触摸（CST9217）、双麦阵列、ES8311 音频链路全部调通，最大的移植风险已被消化 |
| **协议已在我们手里** | v2 WS 协议（16 字节帧头）、OTA/NVS 配置机制均已逆向归档（HARDWARE-LOG §6），receiver 是我们自研的——**设备端和服务端两头都可改** |
| **硬件资源富余** | 16MB Flash（自定义图片/UI 资产充足）+ 8MB PSRAM + LVGL 图形框架现成 + 六轴 IMU（可做佩戴检测/抬起亮屏） |
| **工具链已验证** | esptool 刷机、串口日志、BOOT+RST 恢复流程都已踩坑归档；固件 OTA 可走我们自己的 receiver OTA 通道（已实现），后续升级不走外网 |

**风险与代价**（诚实清单）：
- 开发环境需装 ESP-IDF v6.x（小智主分支已要求 v6），Windows 可用但首次编译较慢（~30-60 分钟）
- Fork 后与上游更新需要自己维护（固定版本、按需 cherry-pick，内部使用可接受）
- 刷机失败风险低（ESP32 几乎刷不死，BOOT+RST 强制下载模式已验证）
- 固件调试需要板子在手 + 串口日志往返，AI 可写代码/分析日志，烧录实测需要人配合

## 3. 需求映射与功能清单（三档）

### A 档：换资源级（无需改逻辑，1 周内）
| 功能 | 说明 | 对应 PRD |
|---|---|---|
| 开机 Logo / 品牌名 | 替换编译期图片资源 | — |
| 待机表盘 | 圆屏时钟/企业 Logo 表盘 | ALL-101 屏显身份（简版） |
| 录音提示音 | 按键/唤醒录音时播放告知音 | **CMP-02/05 录音告知（合规硬约束）** |
| 主题色/字体 | LVGL 主题调整 | — |

### B 档：定制开发级（核心定制区，2-4 周）
| 功能 | 方案 | 对应 PRD |
|---|---|---|
| **服务端推屏** | receiver WS 加 `display` 消息类型（图片/文字/问题），固件渲染全屏页；后台「设备管理」页加推送操作（选设备→传图/发通知） | ALL-401 屏显通知 |
| **设备-人员绑定** | 设备首次联网上报 MAC/EFuse → 后台 devices 表绑定员工（表已建，ALL-601）→ 下发身份信息（姓名/部门/照片）屏显；设备带令牌，未绑定设备仅显示「未激活」 | ALL-101 / ALL-601 |
| **配置锁定** | 配网页增加 PIN 鉴权（PIN 由后台下发）；正式部署后可隐藏配网触发手势；配置改由服务端统一下发（WiFi 凭据加密下发）；进阶：ESP32 NVS 加密 + Flash 加密 | 设备管理 ADM 域 |
| **触摸 UI 页面** | LVGL 页面框架：身份卡页（默认）/录音页（波形+时长+「录制中」红点）/消息列表页/二维码页/设置页（锁） | ALL-102 动态二维码、ALL-401 |
| **一键录音交互** | 物理键长按=录音，屏显录制状态；双击=打打卡/签到（BLE 信标联动考勤 ALL-201） | REC-01 / ALL-201 |
| **消息中心** | 服务端推送待办/审批/会议提醒到屏（文字卡片），触摸翻页 | ALL-401 / ANA-10 待办 |

### C 档：受硬件限制（诚实说明，量产硬件解决）
| 项 | 现状 | 说明 |
|---|---|---|
| 震动提醒 | 板子无震动马达 | ALL-401 的震动部分需量产硬件加马达 |
| NFC 门禁 | 板子无 NFC 芯片 | ALL-301 靠方案商硬件（02 册） |
| 麦克风「硬件级」断电 | 可做软件静音+屏显隐私态 | 真物理断电需量产硬件改电路（CMP-05） |
| 常显身份 | AMOLED 常显耗电+烧屏 | 常显是墨水屏的活（02 册量产方案），AMOLED 用「抬手亮屏」（IMU）折中 |

## 5. 与现有路线的关系

- **内部使用阶段**：开发载体即终端，自研固件直接提升内部体验（品牌/绑定/锁定）。
- **量产路线（D2）不冲突**：方案商 Turnkey 硬件换主控后，自研固件沉淀的 UI/协议/交互设计直接写入 02 册固件需求（FW-xx），服务端协议零改动。
- 若内部试点证明 ESP32-S3 方案够用，量产选型也可考虑同 SoC 路线（思不出位，届时再评估）。

## 6. 多硬件适配策略（2026-09-12 补充：现有三款硬件）

**架构原则：一套核心固件（BadgeCore Fork）+ 板级适配层（board 定义：引脚/屏幕驱动/按键/传感器）+ 服务端按 device 字段区分型号**。小智本身支持 70+ 板型即受益于这套抽象；服务端 receiver 只认协议，`device` 字段已带型号（库表 devices.device_key），新增型号=固件加一块板定义 + 服务端登记，核心协议零改动。

### Passport AI 判定结果：能刷机，纳入 Fork 板级适配（2026-09-12 查证）

FoloToy AI Passport（源自 TRAE AI 创造力大赛纪念勋章，约 $40，另有官方 DIY 套件）硬件底细：

| 项 | 参数 | 对自研的意义 |
|---|---|---|
| 主控 | **ESP32-C3**（单核 RISC-V，8MB Flash） | ESP-IDF 同工具链；音频/OPUS 编码算力弱于 S3，可降复杂度档（小智有 C3 板先例） |
| 音频 | ES8311 编解码 + 麦克风 + 扬声器 | **与 1.75C 同款编解码**——驱动代码可直接复用；有扬声器=提示音/告知音外放 |
| 屏幕 | 240×320 彩色 LCD（非触摸） | 文字通知/身份/状态显示足够，无触摸交互 |
| 连接 | WiFi + BLE + **NFC** | NFC 标签可试验「工牌=门禁卡」（ALL-301 低配预演，取决于 NFC 芯片类型） |
| 交互 | 三枚实体按键 | 一键录音/打卡/ SOS 的物理交互基础 |
| 刷机 | **社区已实战**（Trae 论坛有固件重写帖：改造为随身音乐盒），esptool 串口烧录通用 | 变砖风险与恢复路径明确 |

> 唯一注意：C3 单核对 OPUS 编码有压力，若实时推流吃紧可降级为「本地录音+离线补传」（PRD REC-08 本就要求离线缓存，正好贴合）。

### 各硬件需求差异化要点

- **1.75C（旗舰）**：完整触摸 UI + 推屏图片/问题 + 动态二维码 + 录音状态页——对内演示/试点主力。
- **②③（小屏轻量版，2026-09-12 需求锁定）**：屏幕只显示**文字身份信息——员工名 / 工号 / 职位**（PRD ALL-101 文字子集），辅以录音功能与文字通知；绑定/锁定同旗舰。

### 小屏文字身份显示规范（②③ 通用，数据源=后台绑定关系）

显示内容三项：**姓名 / 工号 / 职位**（绑定生效后由服务端下发，改绑/换岗自动更新；未绑定显示「未激活」+ 设备号后四位）。

| 屏幕 | 版面 | 设计 |
|---|---|---|
| ② SSD1306 128×32 单色 OLED | 极小，2 行 × ~10 字（12px 字体） | 翻页轮显（每 3s）：第 1 页「姓名」，第 2 页「工号」，第 3 页「职位」；录音中固定显示「● 录音中」+时长 |
| ③ LCD 240×320 | 充足 | 同屏全显：姓名（大字）/ 工号 / 职位（中字）+ 底部状态栏（电量/录音中） |

> 中文字库：固件内置 12/16px 中文字体子集（按企业员工姓名动态生成字库或用全量常用字库，Flash 余量充足）。显示数据走现有 WS 通道新增 `identity` 消息（后台 devices 表绑定关系变更时下发），设备端存 NVS 断电保持。

### 对服务端的影响（很小）

- `devices` 表加 `model` 归一化字段；推屏消息按设备能力降级（图片→文字）；协议统一走现有 xiaozhi v2 WS（各板固件都实现同一套）。
