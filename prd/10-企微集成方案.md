## 1. 结论（评估）

**可以集成，改动面小；但既有 PRD 的企微条目优先级倒挂，建议重排为「推送先行、登录后置、组织同步降级」。**

三个判断：

1. **优先级倒挂**。04 册把 SSO（ADM-404）定为 P0，把推送留在无编号无设计状态（06 册 AI-11 一句「站内信/企微推送」带过；09 册 INT-23 只投站内信）。而对内部使用（D22 自己是自己的客户）价值最高、门槛最低的恰是**企微推送**——纪要/行动项/定时报告直接进群，免开后台；SSO 对个位数用户的后台是锦上添花。
2. **门槛错配**。企微扫码登录真实模式要求「Web 网页授权可信域名」（**须 ICP 备案**）+ 可信出口 IP（2022 年后新应用强制，缺则 `gettoken` 报 60020）；当前部署（deploy/docker-compose 内网试驾）不具备，SSO 在阶段 0 即被卡住。群机器人 webhook 则**零凭据门槛**（群里添加即得 URL，只要服务器能出网），当天可通。
3. **复用面大，差异点均有更简解**。BuildCore 方案的适配器模式、模拟模式（D11 惯例）、回调链路语义可整体搬；差异集中在鉴权体系与登录形态（§5.1），BadgeCore 侧反而更简单。

分线结论：

| 线 | 内容 | 优先级建议 | 阶段 0 门槛 | 量级 |
|---|---|---|---|---|
| **W1 企微推送** | S1 群机器人 webhook → S2 自建应用消息（个人级） | **P0（新立，编号 WEC-1xx）** | S1 无门槛；S2 需自建应用三凭据 | S1 0.5~1 人日，S2 +1 人日 |
| **W2 企微扫码登录** | 后台 login.html 扫码登录（首扫自动建号） | **P1（ADM-404 自 P0 降，缩配仅企微）** | ICP 备案域名 + 验证文件 + 可信 IP + 自建应用 | ~1 人日 + 联调 0.5 |
| **W3 组织同步** | 企微通讯录 → depts/users 映射 | **P2（ADM-304 自 P1 降）** | 自建应用 + 通讯录读权限 | 后置，见 §7 |

**放弃项留痕**：钉钉/飞书通道（内部统一企微，适配器留扩展位不实现）；CRM 同步（ADM-403，属对外产品化阶段，内部定位不需要）；企微 JS-SDK（后台仅一个登录页，整页跳转足够）；iframe + postMessage 回调（r 项目实测并无 postMessage——就是回调落在登录页自身、同页读参；BadgeCore 登录页独立整页，整页跳转即可，连 iframe 都不需要）；**密码绑定流程**（r 项目即首扫自动建号，见 §5，绑定/bind_ticket 全套不采用）。

**与冻结发版的关系**：本方案全部改动在 server/（后台），不触固件与 receiver——与当前「冻结发版攒电量数据」约束不冲突，可随时开工。

## 3. 技术基线（集成触点，实测代码为准）

| 触点 | 现状 | 对集成的影响 |

## 4. W1 企微推送（P0，编号 WEC-1xx）

### 4.1 两级通道（S1 先行，S2 凭据到位即升）

| 级 | 通道 | 门槛 | 能力 | 定位 |
|---|---|---|---|---|
| S1 | **群机器人 webhook** | 无（群里「添加机器人」即得 URL；仅 `WECOM_WEBHOOK_URL` env） | 推群、markdown 消息、@手机号提及 | 纪要进群、定时报告进群——内部使用的 90% 价值 |

### 4.2 服务端改动

## 5. W2 企微扫码登录（P1，ADM-404 缩配）

### 5.1 采用 r 项目同款模式（xlogin.html/js 实测）

r 项目实际链路（剥掉 UI 后共 4 步，实测 `xlogin.js` 确认）：

1. 页面加载 → `GET socialAuthCode.do`（r 项目把回调地址写死在前端传参）→ 服务端按 corpid/agentid 构造企微授权链接返回，**state 由服务端生成**；
2. 前端把链接塞进 iframe（400px），员工用企微 App 扫码并在手机上确认；
3. 企微把**登录页自身** 302 到 `xlogin.html?code=xxx&state=yyy`——重载后的页面在初始化时检测 URL 上的 code/state（`checkSocialAuthCallback()`），存在则整页换成 spinner，`POST stateAuthCode.do {socialCode, socialState}`；
4. 服务端 code 换 userid → **自动匹配/创建账号**（r 项目帮助弹窗明写：「首次登录？系统将自动创建您的账号信息」「企业微信登录无需密码」）→ 返回 token → 前端写 cookie 跳首页。

**BadgeCore 照搬其语义，只改一处落点**：BadgeCore 登录页是独立整页，不需要 iframe 嵌码——直接 `window.location = 授权链接` 整页跳过去，企微 302 回 `login.html?code&state`（同页重载），后续与 r 项目完全一致。整页跳转顺带消掉 r 项目 iframe 模式的一个已知小瑕疵（iframe 内已完成登录跳转、外层登录页却还挂着，需手动刷新）。

**不采用的考虑（对照 r 项目简化）**：不做 postMessage/独立回调页（r 项目本就没有，BuildCore 因页内弹层才加）；不做 HMAC 短票（r 项目 state 就是服务端生成、服务端校验，BadgeCore 单进程用内存单次集合同效）；**不做密码绑定流程**（r 项目首扫自动建号；内部使用场景下企微组织成员本就是员工，自动建号默认 `role='sales'` 数据范围最小，admin 后续提权即可——与 login.html 横幅「全员模式」的产品定位一致）。

### 5.2 端点（2 个，挂 /api/auth/ 下，均免登录）

| 端点 | 入参 | 行为 | 返回 |
|---|---|---|---|
| `GET /api/auth/wecom/url` | — | 生成随机 state（`crypto.randomBytes`），存内存集合（含 5min 过期）；live 拼 wwlogin 链接（redirect_uri **服务端按自身 origin 拼**，r 项目前端传 domain 的做法不照搬）；simulated 只回 state | `{mode, url?, state}` |
| `POST /api/auth/wecom/callback` | `{code, state}` | 验 state（存在+未过期+**单次消费即删**）→ code 换 userid（live: `auth/getuserinfo`；simulated: `'wecom-demo'`）→ 查 `users.wecom_userid`：**命中** → `sessions.set` + Set-Cookie（与 /api/login 同构）+ audit `login_wecom`；**未命中** → **自动建号**（name 取企微用户名、重名则用 userid，随机 salt+pass，role='sales'，active=1）→ 落库 → 签发 session | 成功 `{ok, name, role, created?}`；失败 HttpError 现有风格：401 state 无效/过期、401 企微接口异常（不新增错误码族） |

授权链接用**新版端点**（旧 `wwopen/sso/qrConnect` 已停止新接入）：

```
https://login.work.weixin.qq.com/wwlogin/sso/login
  ?login_type=CorpApp&appid={corpid}&agentid={agentid}
  &redirect_uri={encodeURIComponent(login.html 完整地址)}&state={state}
```

### 5.3 前端改动（仅 login.html 一个文件）

- 初始化时同 r 项目 `checkSocialAuthCallback()`：URL 带 code+state → 整页换「正在验证身份…」spinner → `POST /api/auth/wecom/callback` → 成功写提示后 `location = '/'`；失败显示错误 + 「返回登录」按钮（`location.reload()`）。
- 密码表单下方加「企业微信登录」按钮：`GET /api/auth/wecom/url` 拿链接 → live 整页跳转；simulated 显示「模拟扫码登录」，点击后直接 `POST callback {code:'mock', state}`（与 live 同一条代码路径）。
- 照搬 r 项目两态提示即可：加载中 / 失败重试（r 项目的「已扫码待确认」「成功跳转」态依赖轮询，不做）。
- org.html：admin 可禁用/删除自动建出的账号，或清 wecom_userid 让其重扫（现有用户管理页能力范围内）。

## 8. 模拟模式（D11 惯例，凭据未到位不阻塞）

`WECOM_*` env 未配置时：

- **推送**：`pushMode='off'`——站内信照投，audit 记 `wecom_push_simulated`（含本应送达的通道与目标），settings 页显示"未配置"徽标；配置 webhook 后仅 env 变化，代码零改动。

## 9. 安全要点（含一条合规红线）

- secret/webhook URL 仅存服务端 env，前端永不接触；code 换 userid 必须服务端做。
- state 为服务端生成、内存单次消费 + 5min TTL，防 CSRF 与重放（r 项目同款语义；单进程成立，重启后未消费的 state 失效，重扫即可）。
- redirect_uri 固定服务端拼自身 origin，不接受前端传入回调地址（r 项目前端硬编码传 `domain`，属可收窄点，不照搬）。
- session 体系零变更：仍为内存 sessions + HttpOnly cookie，权限判断走现有 role/view_scope。
- **推送出域红线（CMP-07 延伸）**：企微群 = 数据出后台边界。推送到群的内容仅限**已过 redact 双层脱敏的报告结构化摘要**（分析管道本就在脱敏文本上产出，不带原文引用明文——摘要卡只含主题/结论/行动项行，不携带 evidence 原文引用，引用请点链接回后台看）；`wecom_push.enabled` 默认关、仅 admin 可开；**talk 谈话场景默认不推群**（INT-40 红线延伸：谈话纪要仅站内信/仅参会人 S2 点对点），如需放开须在设置页显式配置并留痕。

## 10. 冒烟用例（smoke-test.js 新增 ~12 项）

**W1**：
1. simulated：定时任务触发 → 站内信落库 + audit `wecom_push_simulated`；
2. 配置测试 webhook（指向本地 mock 端点）→ 定时任务触发 → mock 收到 markdown、errcode=0 路径通；
3. 企微返回非 0 errcode → 站内信仍在、audit 记失败（不阻塞主投递）；
4. `wecom_push.enabled=false` → 不推；
5. meeting 收口分析完成 → 纪要摘要 hook 触发一次（不重复）；talk 场景 → 不推群；
6. users 旧库迁移列存在。

**W2**：
7. simulated `/api/auth/wecom/url` 返回 state；
